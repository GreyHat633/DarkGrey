## 1. 结论摘要

- 未发现可直接确认的 P0 级稳定刷物、毁档或必现服务器崩溃路径。
- 找到 5 项应优先处理的 P1 候选：客户端 OpenGL 状态栈破坏、极性碰撞保护绕过、极性碰撞平方级开销、跨世界施法状态残留、网络线程直接修改客户端状态。
- 找到 3 项 P2 候选：SolarFlare 命中跟踪回退、超新星行星重复渲染、按渲染帧生成粒子导致的帧率相关负载。
- 找到 1 组 P3 配置契约问题：若干 JSON/组件参数已读取但运行逻辑未使用。
- “玩家死亡后印记没有消除”在当前实现中**未复现为静态缺陷**：服务端死亡、死亡 Clone、客户端死亡、世界卸载、维度切换和登出均有清理或重同步路径。
- 当前代码通过 `spotlessJavaCheck compileJava --offline`；这只证明格式与编译通过，不代表客户端、独立服务器或多人运行验证通过。

严重度说明：P0=可能立即造成大面积毁档/稳定复制/无法运行；P1=崩溃、严重卡顿、权限绕过或高影响状态错误；P2=中等影响或需要特定条件；P3=潜在配置/维护问题。

## 2. 建议修复清单

### DG-01 [P1，已确认] 碎骨权杖法阵渲染器 OpenGL 状态栈不平衡

**证据**：`ShatteredBoneCircleRenderer.java:77-155`。单次渲染路径执行 2 次 `glPushMatrix`，却执行 3 次 `glPopMatrix`；执行 1 次 `glPushAttrib`，却执行 2 次 `glPopAttrib`。活动法阵每帧都会触发栈下溢，并可能污染随后渲染状态。

**修复前**：法阵存在时，客户端可能出现 OpenGL 错误、后续模型/界面渲染异常、闪烁，严重时可能因显卡驱动或其他模组组合而崩溃。

**建议修复**：让每个 push 与 pop 严格一一配对，并用 `try/finally` 保证异常路径也恢复状态；不改颜色、纹理、几何、粒子数量或运动参数。

**修复后**：画面设计应保持不变，只消除渲染状态泄漏/下溢。需要实机对比法阵出现、持续和结束三个阶段，并检查 OpenGL 错误日志。

**表现影响**：预期无可见差异，可列入第一批修复。

### DG-02 [P1，高可信] 极性碰撞可能绕过 PvP、队友和创造模式保护

**证据**：`PolarityDamageResolver.java:34-76`。参与碰撞的两个主体直接受伤，且范围内实体均可能被击退；只有次级伤害目标经过 `CombatTargeting`。`CombatTargeting.java:13-34` 明确包含 PvP 关闭、队伍友伤关闭及创造模式保护。

**修复前**：在 PvP 关闭、同队禁伤或创造模式下，玩家仍可能作为碰撞主体受伤，附近受保护玩家也可能被击退。

**建议修复**：在直接伤害与击退前统一执行现有 `CombatTargeting` 规则；先确认“极性碰撞是否被设计为无视一切保护”。

**修复后**：受保护目标不再因该机制受伤/被强制击退，普通敌对目标的伤害、击退和表现不变。

**表现影响**：不涉及粒子，但会改变 PvP 游戏规则，必须先由设计方确认。

### DG-03 [P1，高可信，运行影响待压测] 极性碰撞检测呈平方级增长

**证据**：`PolarityDamageResolver` 对参与者进行成对比较，参与者数量增长时比较次数近似 `n²`。该结构是确定的；实际 TPS 下降阈值取决于同时带极性实体数量和服务器硬件。

**修复前**：极性实体密集时，单 tick 检测成本快速上升，可能造成服务器延迟或 watchdog 风险。

**建议修复**：采用空间分桶/邻域索引，只比较可能相撞的实体；必须保持实体 ID 排序、每对只处理一次、伤害公式、击退、冷却与触发顺序完全等价。

**修复后**：高密度场景的比较数量显著下降，正常场景的玩法和视觉结果不变。

**表现影响**：理论上无表现变化，但属于算法替换，需用 100/500/1000/5000 实体压测并对比碰撞结果。

### DG-04 [P1，高可信] 跨世界/维度切换没有统一取消施法和客户端法阵状态

**证据**：

- `BoneMeteorCastState.java:9-49` 保存世界本地时间，却未保存施法起始维度；`BoneMeteorCastManager.java:75-125` 用玩家当前世界时间继续比较。
- `ShatteredBoneStaffCastState.java:10-52` 保存锚点坐标但没有世界/维度；`ShatteredBoneStaffCastManager.java:77-100` 仅按死亡和位移取消。
- `ShatteredBoneCircleRenderer.java:27-63` 的客户端缓存没有明确的世界卸载/维度切换清理，并用新世界时间判断旧状态。
- 1.7.10 的维度传送可复用同一玩家对象，不能依赖对象销毁自然清理正在使用物品状态。

**修复前**：施法中切换维度后，倒计时可能停滞、提前完成、在错误世界继续，或在客户端留下法阵；相同坐标传送器尤其容易保留碎骨权杖施法。

**建议修复**：状态记录起始维度；服务端在维度变化、登出、死亡及世界不匹配时统一取消并发送结束消息；客户端在 `WorldEvent.Unload`、维度切换和登出时清理法阵缓存。

**修复后**：施法一旦离开起始世界即安全取消，不会跨世界结算或残留旧法阵；同一世界内的倒计时、粒子和施法表现不变。

**表现影响**：只删除本不应继续存在的跨世界残留，正常施法表现不变，可列入第一批修复。

### DG-05 [P1，已确认线程违规] BeyondStar 同步消息在网络线程修改客户端状态

**证据**：`api/BeyondStarSatelliteManager.java` 对应同步消息处理器直接修改客户端玩家 IEEP/属性，没有调度到 Minecraft 客户端主线程。

**修复前**：网络线程可能与客户端 tick/渲染并发读写同一状态，产生偶发崩溃、不同步或属性异常；服务端发来的卫星数量也缺少本地边界约束。

**建议修复**：通过客户端主线程任务队列执行更新，并把卫星数量钳制到合法范围（当前设计为 0..8）。

**修复后**：数值和视觉表现不变，消除线程竞态并拒绝越界状态。

**表现影响**：无预期可见差异，可列入第一批修复。

### DG-06 [P2，已确认历史设计回退；运行症状待验证] SolarFlare 冲刺命中记录重新写入玩家 EntityData

**证据**：当前 `ComponentSolarFlare` 使用玩家 `EntityData` 中的 `SolarDashHasHit`；项目既有修复说明要求用 `ScorchedMarkTracker` 的短生命周期集合避免跨死亡/跨维度残留，但当前源码中已不存在该跟踪器。

**修复前**：实现与既定设计不一致；在死亡 Clone、维度切换或异常中断后，旧命中集合有概率使后续冲刺错误地认为目标已命中过。实际 NBT 生命周期症状需要实机验证。

**建议修复**：恢复专用、可明确清理的运行期命中集合；在冲刺结束、死亡、Clone、维度切换和登出时清理。

**修复后**：每次冲刺只在本次生命周期内防止重复命中，不影响灼痕、伤害或特效。

**表现影响**：无粒子变化；可能恢复本应发生但被旧记录错误阻止的命中。

### DG-07 [P2，已确认] 超新星行星渲染器注册了两个不同实例

**证据**：`ClientProxy.java:18-25` 与 `ClientProxy.java:353-358` 分别创建并注册 `SupernovaPlanetRenderer`。两者都会收到 Forge 世界渲染事件，而共享静态状态。

**修复前**：同一个超新星行星可能每帧绘制两次，增加 GPU 开销，并可能叠加亮度、透明度或光晕。

**建议修复**：统一为一个实例，并保证其 tick 与世界渲染事件各只注册一次。

**修复后**：GPU 绘制量下降，但若当前双重绘制已形成用户看到的亮度，画面可能变暗。

**表现影响**：**必须先做截图/录像 A-B 对比并经用户批准，不能直接修。** 若需保留当前亮度，应在单次渲染中显式还原等效强度，而不是依赖重复注册。

> 排除误报：`ShatteredBoneCircleRenderer` 虽出现重复注册调用，但传入的是同一个实例；当前 Forge 事件总线会按目标对象去重，因此不能据此判定它被双重调用。

### DG-08 [P2，高可信] 粒子数量随渲染帧率增长，而不是随游戏 tick 固定

**证据**：

- `ShatteredBoneCircleRenderer.java:126-148` 在 `RenderWorldLastEvent` 中每个活动法阵每帧生成约 6 个粒子，注释意图却是按 tick。
- `PolarityUIRenderer.java:59-98` 在实体渲染后事件中生成粒子，数量同样受 FPS、实体可见性和额外渲染 pass 影响。

**修复前**：高 FPS 玩家生成更多粒子并承担更高 CPU/GPU 开销；低 FPS 玩家反而看到更稀疏的效果，形成反馈性掉帧。

**建议修复**：若获批准，将粒子发射改为固定 tick 预算，并通过单 tick 数量/寿命/透明度补偿，使 20、60、144 FPS 下的时间平均密度尽量一致。

**修复后**：性能和跨 FPS 一致性提高，但粒子密度、节奏或拖尾观感可能变化。

**表现影响**：**纯表现敏感项，不纳入自动修复；必须先给出多帧率录像对比并由用户决定。**

### DG-09 [P3，已确认潜在问题] 配置参数被读取但运行逻辑未采用

**证据**：

- BeyondStar 的 `satelliteLifetimeTicks` 当前与硬编码 160 一致，但修改配置不会改变实体寿命。
- BoneMeteor 的 `materialItemId`、`materialCost` 被读入状态，实际消耗仍硬编码为 `dark_grey:hardened_bone_marrow` 且每次 1 个。
- ShatteredBoneStaff 的 `lockCasterPosition` 被读取，但管理器始终执行位置锁定。

**修复前**：默认 JSON 恰好与硬编码一致，因此当前默认玩法正常；作者调整配置后会无提示失效。

**建议修复**：让运行逻辑使用已解析参数，或删除不支持的参数并在加载时明确报错，避免“看似可配、实际无效”。

**修复后**：默认玩法无变化，自定义配置按文档生效。

**表现影响**：默认配置无差异；自定义参数本来就代表作者主动改变设计。

## 3. 已核对、当前不应列为 BUG 的项目

### 印记死亡/换维度生命周期

- `MarkEventHandler.java:34-75`：玩家死亡时清理；死亡 Clone 清理；非死亡 Clone 才复制；维度切换会重基准时间。
- `MarkContainer.java:78-80`：死亡所有者保存前清空活动印记，载入时也先清理旧映射。
- `ClientMarkCache.java:63-88`：客户端死亡、世界卸载、维度变化及登出均清缓存。
- `MarkTrackingHandler.java:48-80`：维度切换后重新同步本人印记。

结论：当前主印记系统已经覆盖用户特别关心的“死亡后消除”和“切换世界后倒计时继续正确运行”。后续仍要用死亡 Clone、末地门、下界门和自定义传送器做多人实测。

### 其他排除项

- `EntityBoneSpikesField` 已保存/恢复施法者 UUID，无法解析所有者时会删除，并通过 `CombatTargeting` 过滤目标；旧版的无主实体风险当前已修复。
- `UndergroundSunOrbManager.removeAllOwnedOrbs` 的全实体扫描只在生命周期清理事件触发，不是每 tick 热路径，不能仅凭扫描方式判定为持续 TPS 问题。
- 多数技能冷却使用统一 `CooldownHelper`，包含时钟回拨与异常远期值保护；未发现普通换维度即永久失效的明确路径。
- 本轮没有发现可确认的稳定物品复制、玩家存档写坏或世界块数据破坏路径；这不等于多人服中绝对不存在，只表示静态证据不足以成立。

## 4. 推荐审批与修复顺序

1. **第一批，无意图/表现变化**：DG-01、DG-04、DG-05。它们属于状态配对、生命周期和线程安全修复。
2. **第二批，规则确认后处理**：DG-02。先确认极性碰撞是否有意无视 PvP/队伍/创造保护。
3. **第三批，等价性能优化**：DG-03。先建立压力测试和结果对照，再替换算法。
4. **第四批，历史生命周期回归**：DG-06。恢复短生命周期跟踪器并做死亡/换维度矩阵测试。
5. **第五批，必须视觉验收**：DG-07、DG-08。未经截图/录像 A-B 验收不修改。
6. **低优先级配置一致性**：DG-09。

## 6. 证据边界

本清单基于源码、项目既有设计说明、Forge 1.7.10 行为和本地构建。尚未完成真实 Minecraft 客户端、KCauldron/独立服务端、多人 PvP、显卡驱动及大规模实体压测。因此，标为“已确认”的项目是代码结构或契约已经明确错误；其实际崩溃率、TPS 阈值和视觉差异仍需按上表实测。
