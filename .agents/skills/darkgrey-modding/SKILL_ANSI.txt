# DarkGrey 开发规则

先读取仓库根目录的 `.agents/AGENTS.md`，再检查 `git status`、相关源码和实际数据。保留用户已有改动，不要根据旧文档猜测当前架构。

## 1. 明确数据源与发布边界

- 把 `src/main/resources/assets/dark_grey/data/rpg_items.json` 视为发布时的权威物品注册表。
- 把 `E:\Java\MinecraftMod\RPGItem\RPGItems.xlsx` 和 `excel_update.py` 视为编辑/生成源；外部 `rpg_items.json` 不是可单独分发的注册补丁。
- 在启动时允许 `RPGItemDataManager` 用 Jar 内 JSON 覆盖外部工作副本，并把不同的旧文件保存为 `rpg_items.json.previous`。
- 把 `id`、`type` 和 `texture` 视为注册形状。新增、删除、改名或改变注册形状时，重新构建 Jar，并让客户端与服务端使用同一 Jar 后完整重启。
- 只用热重载修改伤害、耐久、附魔和已存在组件的参数。拒绝运行时增删 ID、改变类型/贴图或使用未知组件；解析失败时保留上一份有效配置。
- 服务端重载后把完整有效配置同步给远程客户端；集成服务器本地通道共享单例，不要重复应用。
- 发布版本只修改 `gradle.properties` 中的 `modVersion`，按 `0.1.0`、`0.1.1`、`0.1.2` 递增。运行时产物固定命名为 `dark_grey-<modVersion>.jar`；禁止把 Git 分支、提交数、哈希、`dirty` 或问题描述附加到交付文件名。

## 2. 新增或修改物品的固定流程

1. 先检查工作树、现有物品 ID、类型映射、组件注册和资源文件，避免覆盖用户改动或重复注册。
2. 同步修改 `RPGItems.xlsx`、`excel_update.py` 的 `generate_template()` 默认行、`COMPONENT_GUIDES` 和类型下拉。不要用一次性脚本绕过数据验证，也不要在未核对现有工作簿时盲目执行 `template`。
   - **防回档警告**：在恢复丢失数据或修复配置文件时，**绝对不能盲目使用原始模板直接覆盖**！必须先翻阅历史对话、代码库记录或备份文件，查明该物品此前被修改过的所有定制数值（例如特殊的射程、角度、伤害参数），将它们完整写入 `excel_update.py` 后再执行导出，否则会造成玩家的辛勤调试数据（即“回档”）丢失！
   - **发布防删门**：在编辑工作簿或执行 `export` 前，先从当前 `src/main/resources/assets/dark_grey/data/rpg_items.json` 与最近一次可用运行时 Jar 记录完整的物品数量、ID 集合及每项 `type/texture/components`。除非用户本次明确要求删除或改变注册形状，否则导出结果出现数量下降、任一旧 ID 消失、旧 ID 重命名、`type`/`texture` 改变或组件意外缺失时，必须立即中止；不得把该 JSON 复制到资源目录、运行目录或 Jar。工作簿/模板落后于当前 JSON 时，应先把缺失行与最新注册形状补回工作簿和生成器，再导出，绝对不能让旧工作簿向下覆盖新注册表。
3. 用 `python excel_update.py export` 导出 UTF-8 JSON。逐项比较生成器、工作簿、外部 JSON 与 Jar 资源中的 `id/type/texture/components`。
4. 对照组件的 `configure(JsonObject)` 核对每一个参数名、单位、默认值和上下限；涉及箭数、蓄力等设计常量时必须把实际值显式写入工作簿、生成器和 JSON，禁止只依赖 Java 默认值，也禁止写入不会被代码读取的键。
5. 把最新 JSON 写入 Jar 资源路径。解析时拒绝空 ID、非 `[a-z0-9_]+` ID、重复 ID、未知类型、未知组件和非对象组件条目。
6. 新增组件时，先实现组件/实体/渲染/网络代码，再在 `DarkGrey.preInit` 中注册组件名，最后调用 `RPGItemLoader.loadItemsFromData()`。新增类型时同步增加容器映射、Excel 下拉和模板默认值。
7. 先构造并验证全部物品与组件，再进行任何 `GameRegistry.registerItem`；任一配置失败都中止初始化，禁止留下半套注册表。
8. 生成物品贴图时使用图像生成能力并明确要求透明 PNG。按当前渲染器需要准备背包图标与 `_equipped` 贴图；不要用自动抠白底代替透明源图。
   - **弓类物品贴图强制方向规范**：所有弓类物品贴图（包括主图标与 `_pulling_0~2` 帧）必须严格遵循 Minecraft 原版弓方向：呈 45 度倾斜放置，**左上方为向外弯曲的弓臂（Limb），右下方为弓弦（Bowstring）**。拉弓动画中弓弦与能量箭矢统一向右下方拉扯。任何反向、水平、垂直或异形朝向均属不合规贴图。
9. 发布前递增 `gradle.properties` 的 `modVersion`，运行完整 Gradle `build`，从 `build/libs` 选择 `dark_grey-<modVersion>.jar`；禁止分发 `-dev.jar`、`-sources.jar` 或带 Git/`dirty` 尾缀的 Jar。打开 Jar 验证内置 JSON、关键类和全部预期 ID。
10. 将同一个运行时 Jar 交付给客户端与服务端并比较 SHA-256。遇到 `Fatally missing blocks and items` 时，先比较 Jar 哈希和双方注册日志，不要单独给玩家发送 JSON。

## 3. 注册、ID 与文本规则

- 优先通过 `IRPGItemContainer#getRpgItemId()` 精确比较 ID，例如 `"arrow_of_light".equals(id)`。不要用 `endsWith` 判断物品；它可能误匹配其他后缀相同的 ID。
- `getUnlocalizedName()` 会返回带 `item.` 前缀的名称。只有在无法取得容器 ID 时才精确比较完整值，例如 `item.dark_grey:arrow_of_light`。
- 删除硬编码注册时搜索全部调用方，只移除旧的 `GameRegistry.registerItem` 和确认无引用的类。不要假定 Forge 会安全忽略重复注册；当前加载器应在注册前直接报错。
- 以 UTF-8 保存 Java、JSON、Markdown 和脚本。当前 Gradle 由现代 JDK 运行，不能笼统假定 Windows 一定按 GBK 编译；在旧工具链或易受编码影响的 `switch(type)` 中可使用 Unicode 转义，但必须通过构建验证。
- 组件实例由物品容器共享。不要把“当前玩家、当前目标、当前蓄力”等玩家级可变状态存到组件字段；把状态放进 ItemStack NBT、实体、玩家数据或受控追踪器。

## 4. 服务端权威与多人安全

- 只在服务端消耗弹药、扣除物品、写入决定性 NBT、结算伤害、生成实体和设置冷却；客户端只做即时声音、粒子、动画和预测，并避免同一效果在两侧重复播放。
- 所有 AoE、贯穿、残影、召唤物和爆炸伤害都走 `CombatTargeting.canDamage` 与 `attackEntityFrom`，以保留 Forge/KCauldron 的伤害、死亡、掉落、PVP 和队伍事件链。
- 默认调用 `CombatTargeting.canDamage(..., false)`，排除创造玩家。只有倒悬时针技能可显式传 `true`；它仍应遵守服务端 PVP 和队伍友伤规则。不要把此例外扩散到其他武器。
- 所有爆炸使用不破坏方块的形式，例如 `createExplosion(..., false)`。禁止技能直接调用 `setBlockToAir`、`destroyBlock` 或自行遍历删除方块；需要破坏能力时必须另行接入领地/保护事件并取得用户明确授权。
- 不要用 `setHealth(0)` 后手动调用 `onDeath`。使用 `attackEntityFrom` 进入正常死亡流程，防止双掉落、重复死亡事件、刷物品或绕过保护插件。
- 最大生命值比例、倍率叠加等同一次近战伤害修正必须实现 `IModifyMeleeDamage`，在原始 `LivingHurtEvent` 的 `LOWEST` 优先级中修改伤害；不要依赖 `damageType == "player"` 等容易被 KCauldron 或其他 Mod 改写的字符串，只排除投射物、魔法、爆炸和明确的间接来源。需要无视护甲/抗性时在同一个 `DamageSource` 上保留 `bypassArmor/absolute` 语义；禁止从 `IOnHit` 再调用 `attackEntityFrom`。高血量目标上的第二次完整伤害事件会让 Forge、KCauldron 和保护/战斗插件重复处理，造成数秒级延迟。
- 确实需要独立结算的血祭、爆炸、持续伤害等二次伤害会重新进入 `LivingHurtEvent`。为这类独立伤害增加 `ThreadLocal`/来源标记并在 `finally` 清理，防止组件递归到栈溢出或重复结算。
- 直接命中后又生成贯穿实体时，把首次目标加入排除集合；持续实体必须按实体 ID 去重，防止每 Tick 对同一目标重复造成高额伤害。

## 5. 实体、网络与生命周期

- 给每个临时实体设置明确的服务端 TTL；无有效所有者、从 NBT 恢复后无法重建语义或越界时立即 `setDead()`，不要让孤儿实体永久 Tick。
- 在实体生成前写好决定视觉的字段。使用 `DataWatcher` 或 `IEntityAdditionalSpawnData` 同步蓄力等级、运动方向、起点、视觉领队等状态；不要依赖客户端猜测服务端构造参数。
- 保持实体注册 ID、追踪距离、更新频率稳定。新增消息时在公共侧注册编解码器，把客户端类访问隔离到 `ClientProxy`，并把消息处理调度回客户端主线程。
- 不要给公共构造器、公共字段或公共调用链上必需的方法添加 `@SideOnly(Side.CLIENT)`；专用服务端会把这些成员剥离并导致 `NoSuchFieldError/NoSuchMethodError`。客户端专用实现应放入 client 包或代理。
- 同时检查 Forge 事件总线与 FML 事件总线注册。实体/伤害事件通常走 `MinecraftForge.EVENT_BUS`，玩家/服务端 Tick 和登录事件通常还需要 `FMLCommonHandler.instance().bus()`。

## 6. 性能与视觉表现

- 保留武器标志性法阵、爆炸和轨迹，但必须把粒子数量乘以 `Config.particleDensity` 并设置硬上限。
- 多箭齐射不要让每支箭都生成完整大型法阵。只指定一支视觉领队生成共享法阵，其余箭保留轻量轨迹；把大爆发放在状态切换或命中瞬间，不要每 Tick 重建复杂几何。
- 禁止每 Tick 扫描 `world.loadedEntityList`。使用局部 AABB、事件回调、实体自身更新或有界追踪器；限制半径、实体数量、持续时间和触发频率。
- 对 JSON 可配置的 `arrowCount`、半径、持续时间、伤害、冷却和蓄力设置上下限，并处理 NaN、负数、零蓄力和极大值。低于首阶段的点击释放不得生成投射物，以免创造/无限玩家刷实体。
- 渲染器必须成对执行 `glPushMatrix/glPopMatrix`，用 `try/finally` 恢复矩阵、颜色、混合、剔除和深度状态。先验证实体/物品类型再强转，避免客户端崩溃和后续场景花屏。
- 高分辨率挤出贴图要把真实宽高传给 `ItemRenderer.renderItemIn2D`。缩放后重新居中，但不要把“只调尺寸”变成无依据的挂点位移。
- `Entity#posY` 不是视线高度。眼部位置使用 `posY + getEyeHeight()`；腰部/身体中心优先基于 `boundingBox.minY` 与 `height` 计算，并在玩家、其他生物和不同姿态下验证。

## 7. 当前武器的不可回退约束

- 厄劫使用 JSON 类型 `镰刀`、容器 `ItemRPGScythe`、技能实体 `EntityScythe`。冷却固定为 60 Tick（3 秒），动画总长 20 Tick、第 10 Tick以玩家为圆心结算半径 5 格的水平圆形横扫，实体跟随持有者腰部附近；粒子环、渲染尺寸、伤害半径、伤害时点和实体 TTL 必须同步修改。
- 虹之愿当前读取 `damage1/damage2/damage3`，蓄力阶段固定为 20/40/60 Tick。不要继续使用不会被组件读取的 `chargeTime1/2/3`；若要配置蓄力阈值，先同步实现代码、模板、说明和边界校验。
- 圆环之理当前仍以 `player.onGround` 作为使用门槛，并精确查找主背包中的 `arrow_of_light`。这是用户明确暂缓处理的行为；不要在无新指示时擅自改成其他飞行判定。
- 圆环之理固定释放 30 支光之矢，每支基础伤害 150。`RPGItems.xlsx`、`excel_update.py`、外部 JSON 和 Jar JSON 必须显式记录 `{"damage":150.0,"charge":100,"arrowCount":30}`；不得用空参数对象依赖 Java 默认值。箭阵应在玩家前方组成第一人称可见、以视线为中心的 6×5 水平阵列：生成面垂直于瞄准方向，每支箭沿瞄准方向近似平行前进。禁止改成从玩家头顶垂直落地的 MMO 式箭雨；`RenderMadokaArrow` 不得为空，也禁止让无重力光矢每Tick增加向上速度，否则实体会飞到极高 Y 坐标并在视觉上叠成一支箭。Lore 固定使用“圆环之理 | 万物起源的永恒循环”“必须滞空时才能展开圆环”“至圆环完整”，蓄力不足时不发送聊天提示。
- 枯火杖的 Debuff 免疫以服务端 `PlayerTickEvent` 的当前手持物检查为权威来源，每 Tick调用一次 `IOnHeldTick`；物品 `onUpdate` 只负责客户端手持视觉，不能依赖其 `isSelected` 参数完成服务端免疫。检查负面状态时先验证药水 ID 是否位于 `Potion.potionTypes` 范围内，并隔离异常的 Mod 药水实现；单个药水错误不得把玩家踢出服务器。
- 枯火杖和耀斑长枪的四张贴图固定保留仓库 `HEAD` 中的会话初始版本；用户已明确要求不要再重绘或生成这两件武器的贴图。除非用户以后再次明确授权，否则新增数值或逻辑修改不得触碰 `charred_fire_staff*.png` 与 `solar_flare_lance*.png`。
- 灵气洪流在蓄力移动期间和松手后的持续法阵中均每 10 Tick（0.5秒）结算一次，每次固定读取配置伤害 250；达到最大蓄力半径后只停止扩张，禁止停止后续伤害。只有 `attackEntityFrom` 成功后才施加 20 Tick的反胃、虚弱 II、失明、缓慢 II 和挖掘疲劳 II，并恢复目标原运动量，避免技能击退。两条路径必须调用同一个服务端效果函数，防止伤害或 Debuff 再次分叉丢失。
- 耀斑冲锋只有玩家碰撞盒与合法实体的碰撞盒真实接触时才能结算伤害、击退、反弹、音效和残影。沿本 Tick 位移的扫掠检测只用于把高速移动截停在最早接触点，禁止直接把扫掠候选当作已命中目标，否则第一人称会提前触发；也禁止扫掠盒隔墙选中目标。实体命中由服务端调用 `attackEntityFrom` 确认，只有返回成功后才能施加印记、反弹、音效、击退和残影，再用客户端消息同步反弹速度；客户端真实接触后等待服务器包时不得把水平速度强制清零，否则网络延迟会表现为“先顿住、后爆炸”。禁止客户端自行预测完整命中反馈，否则 PVP、队伍或保护规则拒绝伤害时会出现假命中。墙体中断不能只信任可能滞后的 `isCollidedHorizontally`，还要检查实际水平速度、起步宽限与当前前向的纯方块碰撞盒，不能把友军或其他实体碰撞盒当成墙。保留“跨一格、撞两格”的设计：前方有碰撞后，把玩家碰撞盒抬高一格再次测试，只有仍被阻挡才触发反弹；高草、花等无碰撞盒方块不得触发。撞墙只反弹和播放墙体音效，不生成伤害残影；直接命中的目标必须从 `EntityPhantomStrike` 排除，残影要同步生成数据、限制 15 Tick 生命周期并去重命中。
- 厄瑞波斯攻击力固定为 0，右键冷却 20 Tick，以施法者身体中心为球心的球形半径从 3 格逐次扩大至 7 格；范围判定使用球体与目标碰撞盒相交，禁止退回水平圆形/圆柱体。每次必定施加 4 层剧毒，并分别独立判定 75% 额外 6 层和 40% 再次额外 7 层。两个额外概率禁止改成互斥分支；剧毒稳定期显式传入 200 Tick，连续 100 Tick 不使用后范围重置。
- 伊塔尼斯的普通主箭、额外箭、浮游箭和贯穿箭命中时都必须通过伊塔尼斯专用的独立投射物伤害入口结算，使同一目标在受伤无敌帧内被多支箭命中时每支箭伤害都生效。该入口仍须调用 `attackEntityFrom` 并保留伤害事件链、PVP/队伍校验和命中后的正常无敌帧；禁止改为直接扣血，也禁止全局取消实体无敌帧。
- 耀斑实体命中音效必须由服务端以被撞实体为声源广播；不要把命中声绑到同 Tick高速回弹的玩家位置，也不要只在客户端预测播放。
- 耀斑长枪物品基础伤害固定为 100；冲锋、残影和焦灼引爆仍沿用现有倍率逻辑。修改这一数值时必须同步工作簿、生成器和 Jar JSON，不能只改 Java 技能倍率。
- 百分比最大生命值的“切割”组件已经删除，禁止重新注册或写回 JSON/Excel。替代组件“重击”读取 `intervalSeconds`（默认5秒，0-3600）和 `multiplier`（默认4，0-1000000）；触发时只读取当前手持 `ItemStack#getAttributeModifiers()` 中 `generic.attackDamage` 的物品贡献，并额外追加“武器攻击力 × multiplier”的伤害。禁止直接使用玩家完整攻击属性或当前事件伤害，否则会把力量、暴击、附魔/其他修正重复放大；没有正数攻击属性的空手或非武器不得触发、不得消耗冷却。冷却记录在武器 ItemStack NBT 中，并在原始 `LivingHurtEvent` 上追加伤害；不得创建第二次 `attackEntityFrom`，不得设置无视护甲或绝对伤害。两个参数均应支持现有 JSON 热更新链。每次触发后把“已提示就绪”标志清零，由服务端手持 Tick 在冷却真正结束时仅向持有者发送一次“下一次近战命中将触发重击”提示；切换物品后再次手持也应补发尚未提示的就绪通知。
- 超新星两件套禁止再使用目标最大生命值百分比伤害，也禁止读取或写回 `damagePercent` 或旧的固定伤害参数 `damage`。它与武器重击共用武器攻击力倍率与冷却语义，默认 `intervalSeconds=5`、`multiplier=4`，但使用玩家级独立 NBT 冷却，不能占用或重置手持武器的重击冷却；两者同时就绪时可在同一次近战中分别追加“当前手持武器攻击力 × multiplier”的伤害。超新星重击只允许在 `LOWEST LivingHurtEvent` 的直接近战路径结算，不得被弓箭、魔法或爆炸触发，并由套装 Tick 单独提示“超新星重击”就绪。四件套击杀回满与药水增益保持不变。
- 倒悬时针是唯一允许伤害创造玩家的特例。其他爆炸、镰刀、箭雨、残影和印记爆炸都保持 `allowCreative=false`。

## 9. 第一人称视角：印记 HUD UI 模板 (标准固定格式)

在后续的印记开发中，第一人称 HUD 的渲染必须严格遵循以下 UI 模板，复用已实现的底板、描边和矩阵布局代码，**仅更换对应印记的 32x32 透明像素图标**：

- **图标规范**：严格使用 32x32 像素画。必须确保为完美透明的 PNG，绝对不得残留黑底、白底或任何棋盘格。
- **UI 底板独立设计**：
  - 即使同时拥有多个不同印记，**每一个印记也必须拥有独立的黑底和描边底板，彼此不可连接或共用底板**。
  - 单个印记的底板尺寸固定为宽 `120`，高 `32`。
  - **实心灰黑底色**：无透明度 (`bgColor = 0xFF222222;`)。
  - **灰白立体描边**：上下左右 1 像素内描边 (`borderColor = 0xFFAAAAAA;`)。
  - **缩放比例**：整个 HUD (包括底板和其上内容) 必须通过 `glScalef(0.75F, 0.75F, 1.0F)` 进行 0.75 倍缩放渲染。
- **信息排版 (单个底板内)**：
  - **印记图标**：渲染在底板内 `(6, 6)` 处，大小 18x18。
  - **印记名称与层数**：渲染在 `(28, 6)` 处。无论层数是否 MAX，印记的“名称文字”应永远保持为其主题色（例如剧毒保持为绿色）。
  - **倒计时警报同步闪烁**：稳定期显示 `MM:SS` 格式倒数（如 `0:02`，灰色 `0xAAAAAA`）；当进入衰减期时，固定显示 `0:00`，**字色变红 (`0xFF5555`) 并且与印记贴图图标一起，以 0.5 秒的频率同步不停闪烁警报**。
- **多印记矩阵排版 (HUD 列阵)**：
  - 多个印记从屏幕左上角开始按列向下排列。
  - **列限制**：每一列最多只允许同时堆叠 **4** 个印记。
  - **自动换列**：当同一列已有 4 个印记时，第 5 个印记必须自动在右侧开启新的一列，并从顶部开始堆叠，以此类推。

## 10. 第三人称视角：实体头顶 UI 模板 (Entity Overlay)

第三人称下的实体头上同样需要使用独立分块与金字塔居中对齐的标准化模板规范进行渲染：

- **高度偏移**：UI Y轴偏移量统一使用 `event.y + entity.height + 0.6`，使其悬浮在略高于头部的位置，更加贴合。
- **缩放比例**：必须通过矩阵缩放 `float f = 1.6F * 0.75F;`，将第三人称的全局 UI 大小缩小至 0.75 倍。
- **独立底板与结构**：
  - **同样，每个印记拥有完全独立的、被灰白描边包裹的实心黑底块，严禁将多个印记连在同一个大黑板上**。
  - 每个小底板的高度固定包含 10x10 图标和数字，宽度动态计算（`2 + 10 + 2 + textWidth + 2`）。底板颜色 `0xFF222222`，边缘描边 `0xFFAAAAAA`。
  - **排版结构**：仅渲染对应的小图标（10x10）与层数数字。
  - **数字原色**：即便层数达到 MAX 上限，显示的数字也绝对**不许**突变为高亮绿色，必须永远保持为印记本身的主题色（如剧毒绿）。
  - **衰减同步闪烁**：当印记衰减时，该独立方块内的**小图标和层数数字必须一起同步闪烁**。
- **渲染防闪烁 (Z-Fighting)**：绘制完每个底板后，必须使用 `GL11.glTranslatef(0.0F, 0.0F, -0.01F);` 将前景图标和数字略微推向镜头前，防止与底板发生深度冲突。
- **多印记居中金字塔阵列**：
  - 新印记优先显示在老印记的同排右侧。
  - **行限制**：同一排最多同时显示 **3** 个印记。
  - **自动换行与上推**：当同一排超过 3 个印记时，旧的 3 个印记作为一个整体向上移动一排，第 4 个新印记在下方另起一行，重新开始往右堆叠。
  - **绝对中轴居中**：不论某一行当前有 1、2 还是 3 个印记，该行的所有印记都必须以玩家（或实体）模型的中轴线为基准进行**全局居中、左右对称排列**。

## 11. 目标面板 HUD UI 模板 (准星瞄准时)

当玩家准星指向实体时，屏幕中央偏右下方会显示目标面板 HUD。在多印记环境下，为了防止大量文字霸屏，该面板必须遵循极简的**单行列表**格式：

- **单行极简排版**：不论一个印记有多少数据，**每个印记严格只占用一行（16像素高度）**，彻底废除“距下次触发时间”等多行占位信息。
- **图标前缀**：每行的最左侧必须渲染该印记的微缩图标（12x12 大小），直观区分不同印记。
- **文本格式与主次色彩**：
  - 格式范例：`[图标] 剧毒印记 8层 | 稳定: 9.9s | 预计伤害: 8`
  - 前半部分（名称与层数）必须继承印记本身的主题色（如：`visual.primaryColor`）。
  - 后半部分的辅助信息（稳定时间、衰减时间、预计伤害等）必须使用灰色弱化（代码中使用原版颜色符 `\u00A77`），以突显主次关系，减少视觉杂乱感。
- **扩展性**：未来新增任何类型的印记，其详细状态信息（如特殊 Debuff 量级等）均只能附加在这同一行的辅助信息区域内，严禁强行增加新行破坏版面结构。

## 12. 战斗特效与溅射判定避坑指南

在开发具有高打击感的 AOE / 溅射效果时，必须牢记并避免以下两个“经典陷阱”：

- **粒子特效的物理摩擦力陷阱**：
  - 原版方块碎片粒子（如 `blockcrack`、`iconcrack`）**空气阻力极小（每 tick 保留 99% 速度），但受重力影响明显**。如果试图用这种粒子来做扇形溅射特效，直接给水平初速度会导致它们要么直接落地（速度低），要么像子弹一样飞出二三十格远（速度高），完全无法形成停留在一片区域的爆炸感。
  - **正确做法**：如果需要限定粒子飞行的距离（如 5 格），要么选用自带高空气阻力的粒子（如 `crit` 粒子每 tick 衰减 30% 速度，会自然停顿并悬浮）；如果要强行使用真正的骨头或石头材质碎片（`iconcrack`），则**绝对不能仅靠初速度，必须手写物理抛物线弹道系统**。根据随机落点距离和飞行时间，精确解算水平速度和较低的垂直向上初速，让碎片以平缓迅猛的抛物线“发射并砸落”在指定区域。切记**压低垂直速度（vy）**，否则特效看起来就像火山喷发而不是向前的霰弹枪喷溅。

- **锥形溅射判定的“边缘漏判”陷阱**：
  - 计算扇形/锥形溅射时，如果仅仅计算“攻击源到目标中心点的距离”和“攻击方向与目标中心点的夹角”，会遇到一个致命的体验问题：**体型巨大的怪物（如蜘蛛、史莱姆）或者离得极近的怪物，明明半个身子已经挨到了扇形区域，但因为它的“中心点”偏离了圆弧或角度线，导致判定未命中！**
  - **正确做法（圆锥体与圆柱体相交检测）**：
    1. **距离宽容**：使用 `dist - splashTarget.width / 2.0 <= radius`，把目标的半宽算进攻击半径内，只要边缘蹭到就算距离达标。
      2. **角度宽容**：根据目标距离计算其视觉角宽 `targetHalfAngle = Math.asin(Math.min(1.0, (splashTarget.width / 2.0) / Math.max(dist, 0.5)))`。然后，计算目标中心点的实际夹角 `currentAngle`。只要 `currentAngle - targetHalfAngle <= (扇形总夹角 / 2)`，就意味着目标边缘的圆柱体切入了圆锥体内，必须判定命中。只有使用这种算法，才能彻底解决近战 AoE 边缘漏判的经典手感问题。

## 13. 印记稳定期与衰减参数规范

- 印记分为 `MarkDecayMode.CONTINUOUS`（持续型衰减）和 `MarkDecayMode.INSTANT`（瞬时型衰减）。衰减模式、每次衰减层数和持续型衰减间隔属于印记类型的固有规则，武器、道具和组件不得覆盖这些参数。
- 稳定期属于“本次施加印记”的参数。所有 `MarkApplyContext.Builder` 调用点都必须显式调用 `.stableDurationTicks(...)`；禁止继续使用含义模糊的 `.durationTicks(...)`。
- 若用户没有明确指定稳定期，调用方仍必须显式传入该印记的默认稳定期：剧毒 `200 Tick`（10 秒）、骨折 `100 Tick`（5 秒）、碎骨 `60 Tick`（3 秒）。动态印记 ID 应从 `IMarkType#getDefaultStableDurationTicks()` 取得默认值。
- `MarkManager` 必须保留未传参时使用 `IMarkType#getDefaultStableDurationTicks()` 的兼容兜底，但项目内武器、道具和组件不得依赖这个隐式兜底。
- 稳定期必须存入 `MarkInstance` 并写入 NBT。重新附加印记时用本次传入值覆盖实例稳定期并重置倒计时；瞬时型印记衰减后若仍有层数，必须沿用该实例稳定期重新倒计时，不能偷偷退回类型默认值。
- 持续型典型代表“剧毒”：稳定期结束后进入衰减阶段，固定每 `10 Tick` 衰减 `10` 层，直至归零；重新附加会退出衰减阶段并按新参数重置稳定期。
- 瞬时型典型代表“骨折”：稳定期结束时立即减少 `1` 层，剩余层数大于零则按本次施加的稳定期重新倒计时。独立碎骨默认稳定 `60 Tick`；由满层骨折维持的碎骨是内部生命周期特例，允许显式传入 `0 Tick`，并由维持标志决定移除时机。
- 新增或修改会施加印记的物品时，同步核对 Java `configure(JsonObject)`、`RPGItems.xlsx`、`excel_update.py` 和 Jar 内 `rpg_items.json`。即使 Lore 没写稳定时间，也要把对应默认 Tick 显式写入组件参数，禁止只依赖 Java 字段初始值。

## 14. 默认耐久与跨世界安全规范

### 14.1 未指定耐久时默认无限

- 用户未明确说明耐久度时，所有新工具、武器和装备默认无限耐久；不得根据原版材质、物品类型、附魔或相似物品自行推断有限耐久。
- 在 `RPGItems.xlsx`、`excel_update.py` 模板、外部 JSON 和 Jar 内 JSON 中显式写入 `"durability": 0`，并把 `0` 解释为无限。不得只依赖 Java 初始值或遗漏字段。
- 对原版基类会自动设置耐久的容器，在构造后调用 `setMaxDamage(0)`，并保证 ItemStack 级最大耐久查询返回 `0`，防止剑、弓、工具和盔甲继续沿用 `ToolMaterial`、`ArmorMaterial` 或原版弓的耐久。
- 只有用户明确要求有限耐久时才能设置正数；此时同步四层数据源并确认热重载、耐久条、损坏和修复行为符合说明。原本不可损坏的饰品或道具继续保持不可损坏。

### 14.2 防止世界切换产生时间轴 BUG

- Minecraft 1.7.10 各维度的 `World#getTotalWorldTime()`/`getWorldTime()` 不是全服统一时间轴。禁止把某个世界的绝对 Tick 直接持久化为全局冷却或到期时间，再到另一个世界与当地时间比较。
- 新增或修改功能时，搜索 ItemStack NBT、玩家/实体 NBT、`IExtendedEntityProperties`、静态追踪器和自定义数据中的 `Cooldown`、`Last`、`Expire`、`Until`、`Next`、`setLong/getLong` 与 `getTotalWorldTime()`。凡是状态可能跟随玩家或物品换世界，都必须明确选择下列处理方式：
  1. **短冷却、施法间隔和提示节流**：使用 `CooldownHelper` 保存维度无关的 `*EndMillis`，只在服务端决定是否可用；读取时删除旧的世界 Tick 键，并对系统时钟回拨或异常超长未来值设置上限保护。不要继续保存“上次使用的世界 Tick”。
  2. **必须保持 Tick 语义的印记、异常状态和周期触发器**：继续使用 Tick 计时，但在 `PlayerChangedDimensionEvent` 中计算新旧世界时间差，把稳定期、衰减期、周期触发、到期时间以及嵌套自定义 NBT 中的全部绝对时间戳一起平移，使剩余 Tick 不变。处理器必须注册到 FML 事件总线，并在重新同步客户端状态之前完成平移。
  3. **不允许跨维度存在的临时实体或蓄力实体**：在换世界、死亡、登出和所有者失效时同时清理旧世界与新世界的所属实体；不得留下孤儿实体或把旧世界生成时间拿到新世界排序。若设计明确要求实体跨维度保留，则必须迁移实体并重建/平移全部时间状态。
  4. **只在当前世界、当前 Tick 批次内有效的瞬时状态**：优先使用按 `World` 分组的临时映射、实体 `ticksExisted` 或递减计数器，并设置清理条件；不要写入可跨世界携带的 NBT。
- 世界切换处理不得顺便改变技能位置、轨道、粒子、伤害或冷却长度。死亡/复活还必须单独检查 `LivingDeathEvent`、`PlayerEvent.Clone` 和 NBT 载入清空逻辑，不能假设换世界处理会覆盖死亡生命周期。
- 发布前至少使用两个总世界时间明显不同的维度执行往返测试：分别在首次获得物品、冷却中、冷却结束、蓄力中、携带印记/异常状态以及死亡复活后验证剩余时间和可用状态；静态扫描与构建成功不能替代实际多世界专服测试。

## 15. 绝对死亡 / 即死（Absolute Death）

【保留术语】
当用户在DarkGrey需求中明确提出：
- 即死
- 绝对死亡
- 无条件即死
- 无差别死亡
- 无视一切防御死亡

默认表示调用：
`AbsoluteDeathService.requestAbsoluteDeath(...)`

不得重新实现为：
- 超高伤害
- Float.MAX_VALUE伤害
- 虚空伤害
- 真伤
- attackEntityFrom
- 单独setHealth(0)
- 命令/kill
- 武器组件内复制死亡流程

【语义】
绝对死亡无视：
- 创造模式
- 护甲与抗性
- 咒灵剑
- 星云套
- 无尽套
- DarkGrey免死和濒死机制

【调用规范】
未来武器、Boss、剧情、技能和印记需要绝对死亡时，只调用公共服务，不得复制executeNow实现。

【区分】
用户只说“高伤害”“真伤”“斩杀”“秒杀”时，不自动等于绝对死亡；除非上下文明确或用户使用保留术语。

【回归要求】
任何新增免死/濒死机制都必须显式验证：它不能阻止AbsoluteDeathSource。

## 16. 实体坐标系统与粒子渲染高度（重要教训）

**在 1.7.10 客户端渲染粒子时，切忌直接使用 `entity.posY` 作为实体脚底（0F 点）！**

- **问题原因**：对于玩家（`EntityPlayer`），其 `posY` 代表的是**眼睛的位置（或包含 yOffset 的中心位置）**，而不是脚底。如果你使用 `entity.posY + rand.nextDouble() * entity.height` 来生成粒子，会导致整个粒子效果整体上移，悬空在实体头顶甚至更高处。
- **强制规范**：在任何时候，如果需要基于实体的底部（脚底）坐标来渲染粒子或进行高度计算，**必须使用 `entity.boundingBox.minY`**！
- **正确示范**：
  ```java
  // 错误：posY 是眼睛/中心位置，粒子会飞到天上
  // entity.posY + rand.nextDouble() * entity.height;

  // 正确：boundingBox.minY 才是绝对的脚底（0F点）
  entity.boundingBox.minY + rand.nextDouble() * entity.height;
  ```
- **警钟**：AI 在开发时反反复复犯这个问题，请务必牢记此规范，绝不可再直接基于 `posY` 计算脚底偏移。

## 17. 极性武器与多实体磁力物理规范

- 极性是攻击力 `0`、无限耐久的磁极剑。非潜行右键切换正极/负极；`Shift+右键` 给持有者施加当前极性；攻击给目标施加当前极性。异性印记互相抵消，正负极稳定期均为 `1200 Tick`（60 秒）。Tooltip、Java 默认值、`RPGItems.xlsx`、`excel_update.py`、外部 JSON 与 Jar 内 JSON 必须保持一致。
- 固定磁力公式：实体中心三维距离为 `r`，仅当 `0 < r < 20` 时，`pairAcceleration = 0.20 * (1 - r / 20)^2`；`r >= 20` 时为 `0`。平方衰减不得改成线性、助跑距离、能量累计或长期配对运动历史。`r = 0` 时使用其右极限 `0.20`，方向必须由排序后的实体 ID/UUID 推导出稳定、确定的单位向量，禁止除零、NaN 和每 Tick 随机抖动。
- 每个服务端世界在 `WorldTickEvent.START` 收集带极性印记的实体，按稳定键排序，每个无序实体对每 Tick 只计算一次。异极沿中心连线相互吸引，同极沿连线相互排斥；双方贡献大小相等、方向相反。所有配对贡献先写入独立累加器，全部计算完毕后再对每个实体的本 Tick `magneticDeltaVelocity` 做模长上限 `0.40`，最后一次性加入 `motion`。禁止在配对遍历中边算边改速度，禁止把实体已有总 `motion` 截成 `<= 0.40`。
- `WorldTickEvent.START` 在磁力已加入、实体尚未移动时，为每个实体保存本 Tick 施力前速度、施力后预移动速度、起始碰撞盒和中心。`WorldTickEvent.END` 在实体完成移动后确认实际接触或扫掠接触；爆炸门槛必须读取 START 快照并计算 `closingSpeed = -(velocityB - velocityA) dot directionAtoB`，不得使用任一实体总速度模长、相对速度模长或接触处理后的剩余速度。这样才能包含碰撞前最后一次近距离磁力，并避免 AI、摩擦或原版接触响应覆盖判定速度。
- 高速实体可能一 Tick 穿过对方。碰撞确认必须同时检查结束时 AABB 实际接触和从 START 碰撞盒到 END 位移的连续扫掠 AABB；扫掠只确认本 Tick 是否发生过接触，碰撞点取最早接触时刻。继续保留短期配对去重/重装状态，但状态必须按 `World` 与双方 UUID 隔离，并在世界卸载、印记消失或超时后清理；禁止仅用可复用的 entityId 作为跨时段键。
- 物理管理器必须从 `RPGItemDataManager` 当前已提交的数据版本解析极性组件参数，并在热重载后刷新缓存。禁止永久使用 `new ComponentPolarity()` 的硬编码兜底替代 JSON，否则表格热更新只是表面成功。发布前搜索并清除极性链路中旧的 `12/0.18/0.35`、`24/0.25/0.50`、`0.35/0.70` 等范围、单对强度或净增量限幅残留。
- 撞击伤害公式固定为：`S = clamp(armorA,0,1000) + clamp(armorB,0,1000)`，`L = ln(1 + S/20) / ln(3)`，双方撞击伤害 `round(160 + 300L)`，普通次生爆炸伤害 `round(50 + 150L)`，施加者本人参与两名核心碰撞实体时仅把次生爆炸伤害乘 `4`。核心双方必须先后承受撞击与爆炸两阶段。两阶段无视普通护甲，但属于普通极性派生伤害，不得升级为绝对死亡；相对速度、当前手持物与武器攻击力不得再次加入倍率。爆炸半径保持 `8`，不得破坏方块。
- 必须保留可开关的逐 Tick 诊断，至少记录：距离、单对磁力、未限幅/已限幅净磁力、施力前速度、施力后预移动速度、移动后 motion、投影闭合速度、实际/扫掠接触和爆炸结果。标准回归包括异极初距 `2/5/10/15/19`、同极初距 `1/3/6/10/15`、完全重叠稳定方向、高速一步穿越及至少 10 个正负极混合集群；混合集群必须证明结果不依赖输入遍历顺序且每实体净增量不超过 `0.40`。确定性模拟只证明数学与调度模型，不能冒充真实专服、AI、网络或领地插件联调。
